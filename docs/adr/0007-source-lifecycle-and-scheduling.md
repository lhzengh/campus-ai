# ADR-0007：来源归档、预览与来源级每日调度

- 状态：接受
- 日期：2026-08-21

## 背景

Core 已能创建来源、认证并手动采集，但来源只能使用服务端全局每日时间，Client 也不能安全编辑或移除来源。数据库现有外键允许删除来源时级联删除消息和分析，这不适合作为普通管理操作。与此同时，直接暴露 Cron 会增加用户理解成本、时区错误和补跑语义的不确定性。

## 决定

- 普通删除采用软归档：设置归档时间、停用来源、停止调度、清除 Core 凭据引用并重置认证状态，保留消息、分析和任务历史。
- 已归档来源默认不在列表中；Client 可以显式查看并恢复。恢复后的来源保持停用，避免在用户确认前自动访问外部站点。
- 永久删除来源及其历史数据不属于当前接口，未来必须作为单独的高风险操作提供明确范围和二次确认。
- 来源创建后固定 `connector_id` 与 Connector 版本。更换实现时创建新来源，避免把旧游标或认证会话传给不兼容实现。
- 首版来源计划只支持 `manual` 和 `daily`。每日计划保存当地时间、IANA 时区与下一次 UTC 执行时间。
- Scheduler 每分钟扫描到期来源，以“来源 ID + 计划执行时刻”作为任务去重键。服务停机后只补一次到期任务，然后直接推进到下一个未来时刻，不连续回放所有错过日期。
- 连接检查同步验证 Connector、版本、普通配置和认证状态，但不采集内容。
- 预览通过持久任务最多读取 10 条标准消息；结果裁剪后写入任务诊断，不写消息表、不创建分析任务、不推进来源游标。
- 任务记录保存本次尝试的开始/结束时间、耗时、结构化统计或预览结果和安全错误信息。

## 后果

普通来源管理不会意外销毁历史数据，调度行为也可以在不暴露 Cron 的情况下由不同学校和时区复用。持久任务让慢 Connector 不会阻塞 Client API，并使预览和采集都能统一诊断。

代价是 Scheduler 需要数据库扫描，来源恢复还需要一次显式启用。当前单机 Debian/Compose 规模下每分钟扫描足够轻量；若未来扩展为多调度器或大量来源，需要增加数据库租约或专用调度队列。
